Orchestrated review of `~/Projects/kiln` (Rust workspace: `kiln-core`, `kiln-wasm`, `kiln-cli`).

## 1. Summary

| Severity | Count |
|---|---|
| Critical | 1 |
| High | 13 |
| Medium | 33 |

The 5 findings that matter most:

1. **`q4k_gpu` binds whole-tensor f32 buffers — will fail in every real browser** (`dequant.rs:178`). The Q8_0 embed/LM-head tensors need ~600 MiB per buffer; portable `maxStorageBufferBindingSize` is 128 MiB. Works on the dev GPU only. (Critical, CONFIRMED)
2. **GGUF parser does unchecked arithmetic on untrusted u64s throughout** (`gguf.rs:59-66,244-245,261-300,324-339,368`). Overflow / div-by-zero / giant-`with_capacity` panics or silent wrong bytes on hostile files; several `as usize` casts also diverge on the 32-bit wasm target. (High cluster, CONFIRMED)
3. **GPU error paths `expect`/panic instead of returning `Err` — `panic="abort"` kills the wasm worker** (`compute.rs:23-30`, `hello_compute` → `Vec`, `gpu_ops.rs:21`). Any device loss / map failure / shape misuse traps the module instead of rejecting the JS promise. (High, CONFIRMED)
4. **The diff-harness correctness story currently rests on manual runs**: the only GPU-vs-CPU test is `#[ignore]`d and never runs in CI, Q4_K GPU has no test at all, `model.rs` has zero tests — a forward-pass regression passes CI silently. (High, CONFIRMED)
5. **The numeric ports themselves check out**: Q4_K/Q6_K/Q8_0 CPU match ggml statement-for-statement (spot-verified `get_scale_min_k4` against `ggml-quants.c:880-887`, identical), `f16_to_f32` exhaustively bit-exact over all 65536 inputs, forward pass (NEOX RoPE, QK-RMSNorm order, SwiGLU, GQA mapping, scale) matches the Qwen3 graph with no numeric bug found. The risk is all around the oracle, not in it.

## 2. Critical & High findings (ranked, with verdicts)

### C1. `q4k_gpu` creates and binds unbounded whole-tensor buffers — browser-breaking
- LOCATION: `crates/kiln-core/src/dequant.rs:178` — `let out_bytes = (n_elements * 4) as u64;` feeding `out_buf` (`:179-184`, `size: out_bytes`), `readback` (`:185-190`), `as_entire_binding()` (`:220`), `copy_buffer_to_buffer(..., out_bytes)` (`:240`).
- CLAIM: Dequantizing `token_embd.weight` / `output.weight` in one call exceeds the browser `maxStorageBufferBindingSize` and fails on default Chrome/Safari while passing on the dev GPU.
- EVIDENCE: Q6_K LM head is 155M elems → 593.5 MiB f32 (`docs/spikes.md:168`); portable baseline is 128 MiB binding / 256 MiB buffer (`docs/spikes.md:26-28,82-84`). Dev GPU reports 2047 MiB (`docs/spikes.md:18-19`), hiding the cliff.
- FIX: Check `out_bytes` against `ctx.report.max_storage_buffer_binding_size` / `max_buffer_size` and return `Error::Shape`, or chunk into ≤128 MiB dispatches. Never bind a whole embedding/head tensor at once.
- VERDICT: **CONFIRMED** (read all three buffer sites; no limit check anywhere in the file). Latent today (unwired from wasm) but it is the next thing to be wired.

### H1. `read_buffer` converts recoverable GPU failures into panics (aborts wasm module)
- LOCATION: `crates/kiln-core/src/compute.rs:23-30` — `let _ = ctx.device.poll(...); rx.await.expect("map_async callback dropped").expect("buffer map failed"); ... .expect("get_mapped_range after successful map")`.
- CLAIM: Device loss / OOM / validation failure during map panics instead of returning `Err`; under workspace `panic="abort"` (`Cargo.toml:32`) this traps the WASM worker instead of rejecting the JS promise `web/worker.js` is ready to handle.
- EVIDENCE: Reachable today via `kiln-wasm::probe()` (`kiln-wasm/src/lib.rs:25` → `hello_compute` → `read_buffer`). `map_async` documents a `Result`-carrying callback; the poll result is discarded.
- FIX: Return `crate::Result<Vec<u8>>` mapping oneshot-cancel / `BufferAsyncError` / poll errors into a new `Error::Gpu` variant; make `hello_compute` return `Result`.
- VERDICT: **CONFIRMED**. (Subagents 5 and 6 converged independently on this.)

### H2. `hello_compute` cannot fail by signature — every GPU error must panic
- LOCATION: `crates/kiln-core/src/compute.rs:39` — `pub async fn hello_compute(ctx: &GpuContext, input: &[f32]) -> Vec<f32>`.
- CLAIM: With no error channel, shader-compile / validation / map failures have no path to JS except a trap; contrast `gpu::acquire`, which correctly maps to `JsError` (`kiln-wasm/src/lib.rs:20-22`).
- FIX: `-> crate::Result<Vec<f32>>`; update the two callers (`kiln-wasm/src/lib.rs:25`, `kiln-cli/src/main.rs:161`).
- VERDICT: **CONFIRMED**.

### H3. GGUF `Cursor::take` overflows on attacker-controlled length before bounds-checking
- LOCATION: `crates/kiln-core/src/gguf.rs:324-328` — `.get(self.p..self.p + n)`.
- CLAIM: A hostile string-len / array-count (`u64::MAX`) makes `self.p + n` overflow `usize`: panic in debug/test builds instead of `Err` (release happens to return `None` via wrapped range, but only by accident).
- FIX: `checked_add` → `Error::Gguf("header truncated")`.
- VERDICT: **CONFIRMED**.

### H4. Untrusted `u64` counts truncated with `as usize` — diverges on wasm32 (the primary target)
- LOCATION: `crates/kiln-core/src/gguf.rs:261-262` (`tensor_count`, `kv_count`); same pattern at `:280` (`n_dims`), `:339` (string len), `:368` (array count), `:244` (`t.offset as usize`).
- CLAIM: On `wasm32-unknown-unknown` (`usize` = 32 bit) the same file parses to different table sizes than on 64-bit native.
- FIX: `usize::try_from(...)` mapped to `Error::Gguf`, plus sanity caps, at every file-data `u64 → usize` cast.
- VERDICT: **CONFIRMED**.

### H5. Attacker-controlled counts pre-allocated without validation (tiny file → abort/OOM)
- LOCATION: `crates/kiln-core/src/gguf.rs:264` (`HashMap::with_capacity(kv_count)`), `:277` (tensors), `:281` (`Vec::with_capacity(n_dims)`), `:369` (array items).
- CLAIM: A ~30-byte header (`kv_count = u64::MAX`, `n_dims = u32::MAX`) forces a huge reservation before any length check — classic untrusted-input DoS, browser-breaking for a WASM loader.
- EVIDENCE: Real values are tiny (dims ≤ 4 per ggml `GGML_MAX_DIMS`, KV/tensor counts in the hundreds).
- FIX: Cap before reserving (`kv/tensor ≤ 10_000`, `n_dims ≤ 4`, array `count ≤ 1<<28`) or grow incrementally / `try_reserve` → `Err`.
- VERDICT: **CONFIRMED**.

### H6. `raw()` wraps on untrusted offset — can silently return wrong tensor bytes
- LOCATION: `crates/kiln-core/src/gguf.rs:244-245` — `let start = self.data_start + t.offset as usize; let end = start + t.n_bytes();`
- CLAIM: On overflow the wrapped range can still satisfy `slice::get` and return header bytes as "weights" — silent garbage downstream (`model.rs:102`, dequant), not even a panic.
- FIX: `checked_add` + `usize::try_from` on the offset, all mapped to `Err`.
- VERDICT: **CONFIRMED**.

### H7. `n_elements()` / `n_bytes()` wrap and truncate silently
- LOCATION: `crates/kiln-core/src/gguf.rs:59-66` — `self.dims.iter().product::<u64>() as usize`; `self.n_elements().div_ceil(blk_elems) * blk_bytes`.
- CLAIM: Dims `[2^32, 2^32, 64]` wrap the product to 0 → `n_bytes() = 0` → `raw()` returns an empty slice as success. Any count `> u32::MAX` truncates on wasm32.
- FIX: `checked_mul` fold + `try_from` + `checked` div-ceil, mapped to `Error::Gguf("tensor too large")`.
- VERDICT: **CONFIRMED**.

### H8. `general.alignment = 0` panics the parser (div-by-zero); negatives wrap huge
- LOCATION: `crates/kiln-core/src/gguf.rs:271-275` (`.map(|v| v as u64)`, so `-1 → u64::MAX`) + `:300` (`pos.div_ceil(alignment as usize) * alignment as usize`).
- CLAIM: A well-typed corrupt file panics in `Gguf::open`/`parse` instead of `Err`. Llama.cpp rejects 0; spec default is 32.
- FIX: Reject `a == 0 || a > (1<<30)`; use checked arithmetic + `try_from`.
- VERDICT: **CONFIRMED**.

### H9. `U64 > i64::MAX` wraps negative; negatives become huge `usize` → far-away giant allocs
- LOCATION: `crates/kiln-core/src/gguf.rs:97` (`Self::U64(v) => *v as i64`) feeding `:183-186` (`.map(|v| v as usize)` in `need_usize`) and the same `v as usize` at `:200` (`key_length`), `:207` (`vocab_size`), `:224` (`head_count_kv`).
- CLAIM: `qwen3.block_count = -1` → `n_layers = usize::MAX` → `Vec::with_capacity(usize::MAX)` aborts in `Model::load` (`model.rs:53`); `embedding_length = -8` similarly. One metadata edit, crash far from cause.
- FIX: `i64::try_from` in the `U64` arm; `usize::try_from(v).ok()` (rejects negatives) in `need_usize` and all three fallback maps.
- VERDICT: **CONFIRMED**.

### H10. `head_dim` fallback divides by zero when `attention.head_count = 0`; `dims[1]` indexing panics
- LOCATION: `crates/kiln-core/src/gguf.rs:197-201` (`.unwrap_or(d_model / n_heads)`) and `:213` (`.map(|t| t.dims[1] as usize)`).
- CLAIM: Missing `key_length` + `head_count = 0` → `1024 / 0` panic in `config()`; a 1-D/0-D `token_embd.weight` panics instead of `Err`.
- FIX: Require `n_heads > 0` (or make `key_length` required); `t.dims.get(1)` + `try_from` with a proper error.
- VERDICT: **CONFIRMED**.

### H11. `Model::forward` panics on out-of-range token ids — reachable end-to-end from the CLI
- LOCATION: `crates/kiln-core/src/model.rs:99-105` (`self.tok_embd[off..off + c.d_model]` with `off = t as usize * c.d_model`); `forward` returns `Vec<f32>`, not `Result`.
- CLAIM: `kiln forward model.gguf --tokens 999999999` index-panics instead of erroring; the CLI parses arbitrary `u32`s with no vocab check (`kiln-cli/src/main.rs:50-56`).
- FIX: Bounds-check ids against `c.vocab_size` and change `forward` to `Result<Vec<f32>>` (matching `Backend::step`).
- VERDICT: **CONFIRMED**. (Empty-input `forward(&[])` → `h[seq-1]` panic at `:184` is real but CLI-guarded (`main.rs:68-70`); pub-API-only, hence Medium — see M9.)

### H12. CI only builds the wasm `dev` profile — release `wasm-opt` SIMD flags never validated
- LOCATION: `.github/workflows/ci.yml:34` (`wasm-pack build ... --dev`) vs `crates/kiln-wasm/Cargo.toml:31-40` (release `wasm-opt` with `--enable-simd` etc.; dev sets `wasm-opt = false` at `:42-43`).
- CLAIM: The load-bearing decided-stack flags (CLAUDE.md:29-30) are skipped by exactly the build CI runs; a SIMD-validator mismatch can only be caught locally.
- FIX: Add a `--release` wasm-pack step (or switch dev→release).
- VERDICT: **CONFIRMED**.

### H13. Only automated GPU-vs-CPU diff test is `#[ignore]`d — CI can never run it
- LOCATION: `crates/kiln-core/src/gpu_ops.rs:119-121` (`#[ignore = "requires a WebGPU adapter"]`) + `.github/workflows/ci.yml:22` (no `-- --ignored`; `ubuntu-latest` has no GPU anyway).
- CLAIM: A forward-pass-affecting kernel regression passes CI silently; the spike table documents the `--ignored` manual invocation.
- FIX: Keep `#[ignore]`; add a GPU-runner job or Lavapipe trial (`WGPU_BACKEND=vulkan`), and mark the spike table "manual, not in CI" until then.
- VERDICT: **CONFIRMED**. (Subagents 7 and 8 converged.)

### H14. Q4_K GPU-vs-CPU has no test at all; `model.rs` has zero tests
- LOCATION: `crates/kiln-core/src/dequant.rs:158` (`q4k_gpu` called only from `kiln-cli/src/main.rs:227`, tests at `:260-336` CPU-only); `crates/kiln-core/src/model.rs` (205 lines, no `#[cfg(test)]`; `forward` at `:89`, EOF at `:205`).

- **M3. `config()` validates no ranges** (`:216-235`). Zero/huge dims pass parsing and explode in `model.rs` (`head / gqa` div-by-zero at `model.rs:141` when `n_kv_heads == 0`; `with_capacity(usize::MAX)`). Check `> 0`, `n_heads % n_kv_heads == 0`, `checked_mul` dims. CONFIRMED.
- **M4. `head_dim` fallback `d_model / n_heads` silently wrong for Qwen3-0.6B (64 vs true 128)** (`:197-201`). In-bounds but wrong logits; `matmul_vec` guards are `debug_assert`-only (`ops.rs:24-26`). Make `key_length` required or validate against `wq` element count. CONFIRMED (trigger needs absent key — verify against a real file dump).

- **M6. Zero automated parser tests** (`:251` `parse`, `Cursor::*`, `config/raw/tensor`, `n_elements/n_bytes`, `MetaValue::as_*`). Only exercised via gitignored `.gguf` files. Add in-memory GGUF v3 blob tests (bad magic/version/truncation/alignment/missing keys). CONFIRMED.

- **M11. `dequant_cpu` dispatcher and `max_error` have zero direct tests** (`:26`, `:248`). F32/F16 arms uncovered; the `1e-6` floor never runs in CI. Route each dtype through `dequant_cpu` in tests. CONFIRMED.
